Simple definition

How much work is visibly going into a project's code: commits, contributors, releases. It is used as a sign of life, and it is easy to fake.

Professional definition

A family of indicators drawn from public code repositories — commit counts, distinct contributors, issues closed, release cadence — used in project diligence as evidence that a protocol is still being built and maintained rather than abandoned.

Technical definition

Commit counts are the weakest member of the family and the most quoted. A commit is an arbitrary unit of work: one can be a whitespace change and another a consensus rewrite, and automated dependency updates generate them endlessly. Contributor counts are stronger but inflated by one-line fixes and by the same person using several identities. None of these metrics observes the private repositories where much protocol work happens, and none measures code quality or security.

Academic definition

A set of observable repository-derived indicators used as proxies for the maintenance effort and continuity of a software project, none of which is a validated measure of software quality.

Mechanism

The metric is a count of events in a version-control system, and a version-control system records whatever is pushed to it. Because the unit of work is defined by the contributor, not by the measure, the series can be raised at will: split one change into fifty commits, enable an automated updater, or open and close trivial issues. What it detects reliably is abandonment, not quality.

In practice

Who uses it
Analysts screening projects, grant and treasury committees, data providers publishing ecosystem rankings, and auditors scoping a review.
Why it matters
A repository that has had no commits and no releases for a year is strong evidence of abandonment, and that is a conclusion worth reaching cheaply.
Limitations
The metrics measure visible effort, not quality, security or delivery, and every one of them can be inflated by a contributor who wants to.

Common mistakes

  • Ranking projects by commit count.
  • Treating a bot's dependency updates as development.
  • Assuming no public activity means no development, when work may be private.

Examples

numeric

Repository A shows 2,400 commits in a year from 3 contributors, of which 1,440 are automated dependency bumps. Repository B shows 400 commits from 25 contributors. Commit count ranks A six times higher; contributor count reverses the order.

Given
  • Repository A: 2,400 commits, 3 contributors, 1,440 automated commits
  • Repository B: 400 commits, 25 contributors, no automated commits
Steps
  1. A human commits = 2,400 - 1,440 = 960
  2. A commits per contributor = 960 / 3 = 320
  3. B commits per contributor = 400 / 25 = 16
  4. Ranking by raw commits: A / B = 6.0
  5. Ranking by contributors: B / A = 8.3
Opposite rankings from the same two repositories depending on the metric chosen

Illustrative figures. Neither ordering says anything about code quality, test coverage or security.

case

A project advertises a top-ten position in a developer ranking. The repository turns out to hold mostly documentation and configuration, with the protocol code in a private repository that the ranking never saw — in either direction the public metric answered a different question.

Commonly confused with

Smart Contract Audit

Developer activity counts how much code was written. An audit is an expert review of what that code does. High activity with no audit is a larger risk than low activity with a published audit.
