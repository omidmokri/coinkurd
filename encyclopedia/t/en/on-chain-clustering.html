Simple definition

Grouping blockchain addresses that probably belong to the same holder, using patterns in how coins are spent. It is a guess about ownership, not a record of it.

Professional definition

The use of spending heuristics to assign addresses to inferred entities. The two workhorses are common-input ownership, which groups addresses co-spent in one transaction, and change-address identification, which follows the output returned to the sender. Both produce probabilistic attributions that can merge unrelated parties.

Technical definition

Inference of an ownership partition over addresses from transaction structure. Common-input ownership assumes that all inputs to a transaction were controlled by one party, which collaborative spending protocols and exchange batching violate by design. Change identification relies on recognisable patterns in output structure and breaks when wallets randomise. Errors compound: one wrong merge joins two entities permanently and every later inference inherits it, so clusters grow more fragile as they grow larger.

Academic definition

The heuristic inference of entity-level ownership partitions over blockchain addresses from transaction-graph structure, yielding probabilistic rather than identifying attributions.

Mechanism

A public ledger hides names but publishes structure, and structure leaks. To spend several coins at once a wallet must sign them together, which is evidence that one key holder controlled all of them, and returning change creates a recognisable output. Both leaks are side effects of ordinary use, not mistakes, which is why privacy tools work by deliberately making the same structures ambiguous.

In practice

Who uses it
On-chain data providers, compliance and investigative teams, researchers measuring holder behaviour, and privacy researchers testing how well heuristics fail.
Why it matters
Address-level data is unusable for most questions about behaviour, so some entity grouping is needed before any holder-level metric can be computed at all.
Limitations
Clustering is probabilistic attribution, not identification. It never establishes who a party is, and false merges carry real privacy consequences for people wrongly linked.

Common mistakes

  • Reporting a cluster as a named owner.
  • Applying one chain's heuristics to a chain with a different transaction model.
  • Treating a clustered holder count as a count of people.

Examples

crypto

A collaborative spending protocol deliberately puts inputs from many unrelated users into one transaction. Common-input ownership then merges all of them into a single cluster, producing one apparent holder that in fact never existed.

numeric

Suppose a heuristic merges unrelated parties in one case in twenty, and a cluster was built by chaining eight such links. The chance that none of them is wrong is about 66%, so roughly a third of comparable clusters contain at least one false merge.

Given
  • assumed per-link error rate = 0.05 (an assumption for the arithmetic, not a measured rate)
  • number of chained links in the cluster = 8
  • errors assumed independent across links
Steps
  1. P(no error) = 0.95^8
  2. 0.95^8 = 0.6634
  3. P(at least one false merge) = 1 - 0.6634 = 0.3366
about 34% chance the cluster contains a false merge

The 5% figure is illustrative. No source in this encyclopedia's registry publishes an audited false-positive rate for these heuristics, which is itself the point: the error rate is unknown, not small.

Commonly confused with

Active Addresses

Active addresses counts address identifiers that moved coins. Clustering tries to collapse those identifiers into inferred holders. One is a direct count from the ledger; the other is an estimate layered on top of it.
