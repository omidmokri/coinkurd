Multisignature

Simple definition

A balance that needs several keys to move, not one. In a two-of-three setup, any two holders can sign, so losing one key is survivable.

Professional definition

A rule, enforced by script or contract, that a transaction is valid only once m of n designated keys have signed. It removes the single point of failure: no one key can spend, and up to n minus m keys can be lost without locking the funds.

Technical definition

The quorum m sets both risk dials at once. Raising m makes theft harder, because an attacker needs m keys, and loss more likely, because only n minus m may fail; lowering m does the reverse. The guarantee holds only if the keys are genuinely independent: different devices, locations and holders. Three keys derived from one seed, or three backups in one drawer, are one key wearing three hats.

Academic definition

An access-control scheme requiring a threshold m of n authorised signatures to validate a transaction, parameterising the trade-off between unauthorised spending and irrecoverable loss.

Mechanism

A single key fails in two opposite ways: it can be stolen or it can be lost, and hardening against one usually worsens the other. A threshold scheme separates them by distributing trust across n holders, so an attacker must compromise m places while the owner can still afford to lose n minus m.

In practice

Who uses it
Exchange and fund operations, DAO treasuries, partnerships and family holdings, and individuals splitting keys across locations.
Why it matters
It makes a single stolen or lost key survivable and forces more than one device or person into every spend.
Limitations
It adds coordination cost and new failure modes: unavailable signers, undocumented quorums, and backups that quietly collapse back into one point.

Common mistakes

  • Deriving every key in the scheme from one seed phrase.
  • Storing all the backups in the same building.
  • Never running a recovery drill with one signer removed.

Examples

numeric

Two-of-three tolerates one lost key and needs two for theft. Three-of-five tolerates two losses and needs three for theft. Raising the threshold buys resistance to theft and spends resistance to loss.

Given
  • Scheme A: m = 2, n = 3
  • Scheme B: m = 3, n = 5
  • Keys assumed independent in device, location and holder
Steps
  1. A: losses tolerated = 3 - 2 = 1; keys an attacker needs = 2; authorising subsets = C(3,2) = 3
  2. B: losses tolerated = 5 - 3 = 2; keys an attacker needs = 3; authorising subsets = C(5,3) = 10
A tolerates 1 loss and resists 1 theft; B tolerates 2 losses and resists 2 thefts

These are counts, not probabilities. Independence is the whole assumption: if two of the keys share a device or a backup location, the real thresholds are lower than the labels.

market

A DAO treasury runs four-of-seven with signers on separate devices in separate countries. One signer's laptop is compromised; the attacker holds one key out of four needed and the treasury does not move.

Mathematical foundation

\text{authorising subsets} = \binom{n}{m} = \frac{n!}{m!\,(n-m)!}, \qquad \text{losses tolerated} = n - m, \qquad \text{keys needed to steal} = m

Variables

Procedure

Fix n, the number of keys you can genuinely keep independent. Choose m. Losses tolerated is n minus m; keys an attacker must collect is m; the number of authorising combinations is n choose m. Read the two edges: m equal to 1 is a single key with spares, m equal to n locks the funds if any one key is lost.

Worked example

Given
  • n = 3
  • m = 2
Steps
  1. Losses tolerated = 3 - 2 = 1
  2. Keys an attacker needs = 2
  3. Authorising subsets = 3! / (2! x 1!) = 3
Two-of-three: 3 authorising pairs, 1 key may be lost, 2 keys must be stolen

Interpretation

The three quantities are the whole design decision. m is how many independent compromises an attacker must achieve; n minus m is how many independent failures you can absorb. Everything else is operations: who holds what, where the backups are, and how a signer is replaced.

Assumptions

  • The keys are independent: distinct devices, holders and backup locations, and not derived from one seed phrase.
  • The counts are combinatorial. They say nothing about the probability of loss or theft, which depends entirely on how the keys are actually distributed and operated.
  • Enforcement differs by chain: Bitcoin uses script-level multisig, Ethereum a contract, and threshold-signature schemes produce a single signature from m shares, which is a different construction with the same m-of-n policy.
Limits of the formula
  • The formulation protects against single-key failure, not against one person controlling several keys, nor against all required signers approving the same malicious transaction.
  • As n grows the process cost grows faster than the security benefit: drills, signer changes and documentation all have to scale with it.

Commonly confused with

Social Recovery

Multisig requires a quorum for every spend. Social recovery leaves spending to one key and uses a quorum only to replace it.

The maths block is combinatorial counting, not a risk model: it deliberately states that the subset counts carry no probability. No threshold is recommended, because the right m depends on how many places the holder can genuinely keep independent.
